# Process And Staffing decisions

Team practices, experiments, staffing, review, and decision-making rules.
Product delivery and benchmark rules belong in their own area files.

## In force

- [D12](#d12) — Experiment E1 (true mobbing) stays open and opt-in behind a flag, not the default practice; its numbers are labelled early data. Follows D8
- [D15](#d15) — Tooling standard: a hardened smoke check before first use, non-author review of tooling, rotation authorship with logged takeovers

- [D22](#d22) — Atomic land-or-discard runs are an experiment (E3); dependency-free work may run in parallel, dependent or shared-state work stays at WIP of one

- [R4](#r4) — Staffing is by role first and model second
- [D101](#d101) — Docs state principles and rationale, not who said them; no personal names, no verbatim quotes attributed to a role, no gendered pronouns about the sponsor
- [D109](#d109) — Decider seats are by role, not by model

#### Decider D109: Decider seats are by role, and decisions stay reversible

- Date: 2026-10-28. Question: how is the Decider seated when a model runs out of credits, and what keeps a wrong call cheap now that fewer models review. Decided as a standing principle by the product owner (no design dispute); recorded here and in the working agreement and the mob-defaults template. Result: passed.
- Decision: (1) Decider seats are by role, not by model. Every role is seated; each seat is filled by an available model in a fresh context; one model may fill several role-seats (never reviewing its own authorship); a vote is never taken with fewer seats because a model is out; the decision record names which model filled which role-seat. Reason: the diverse perspectives come from the roles, and a shrinking vote quietly weakens every decision. (2) Decisions stay reversible: each card, commit and decision is small enough to revert cleanly on its own; a decision that cannot be undone cheaply is flagged as a one-way door and escalated as the Escalation section says, otherwise it is split until it can be undone; the record names the revert step. Reason: with fewer models reviewing a wrong call is more likely, and cheap reversal is the safety net.
- Effect now: Grok is out (usage balance exhausted); the roles it filled are filled by Codex and fresh-context Claude seats. D100 to D108 listed the seats that voted; from D110 each record lists the role, the model that filled it and the context (fresh or not).

#### Decider D137: outside-in TDD under trunk-based main (the pending-test mechanism)

- Date: 2026-10-29. The product owner defined outside-in TDD (the text is in TEAM_WORKING_AGREEMENT.md, Practices): for one acceptance criterion, write a failing acceptance test first; identify the layer it consumes; build that layer with unit-level TDD using test doubles for its dependencies; then build the real implementation of each dependency from the layer above in the same way, again with doubles for its dependencies, until enough is built for the acceptance test to pass; the acceptance test fails during all of this until the last unit is built; then the next criterion. Addendum from the product owner: use ZOMBIES (Zero, One, Many, Boundaries, Interface, Exceptions) to find all of the acceptance criteria and each of the unit tests at each layer. The definition is not weakened. Question to the Decider: under trunk-based main with a green gate on every push, how does a committed but still failing acceptance test avoid turning main red.
- Seats by role (D109): architect, Codex: Yes (the mechanism below; alternatives rejected: a local-only red test leaves no auditable red commit, a skip attribute cannot prove failure, a separate excluded project can drift outside normal test execution). Independent auditor lens, Claude (Sonnet), fresh context: No on the first mechanism with five changes, all adopted. Result: passed on the adopted wording.
- Mechanism. (1) The red commit adds the acceptance test for ONE criterion with two traits: Status=Pending (already excluded from the gate by the filter Status!=Pending) and Criterion=NNN-K (card and criterion number). (2) Unit commits follow, layer by layer from the outside in, each green in the gate, each adding or changing a unit test file under the layer it builds (the file is named in the record) with test doubles for the dependencies. (3) The green commit removes Status=Pending from the acceptance test in the same commit that makes it pass; the acceptance test body is byte-identical from the red commit to the green commit apart from the traits. (4) A CI job pending-red runs the tests that carry Status=Pending and a Criterion trait and requires them to FAIL by assertion failure only (never by a build or discovery error); a pending test that passes fails the job (remove the marker). (5) The checker fails when more than one Criterion-tagged test is Pending at once, when a Criterion-tagged Pending test belongs to a closed card, when a Pending test has no record entry, or when a record criterion marked done still has Pending. (6) The trail record gets, per criterion, an entry criterion, acceptance_test, red_commit, unit_commits (in order, each with the unit test file it touches) and green_commit; the checker verifies against git log order (never the record alone) that the commits exist on main, the order red then units then green, that the red commit adds the named test with Pending and Criterion, that the green commit removes Pending from it, that the test body is unchanged, that each unit commit touches the named test file, and that criterion K+1 red comes after criterion K green. (7) ZOMBIES at both levels (added by the facilitator on the owner addendum; the seats were not re-polled, the checker card reviews it): the card acceptance criteria are derived with ZOMBIES, and the trail record lists, per card, the criteria with the ZOMBIES letters they cover, and per unit commit (per layer) the unit tests derived with ZOMBIES as zombies: one entry per letter Z, O, M, B, I, E, each either the name of a test that exists in the named unit test file at that commit or the text N/A because followed by a non-empty reason; the checker fails when a letter is missing, a named test does not exist in the file at that commit, or an N/A has no reason; every unit test uses doubles for the layer dependencies. (8) Judgment is FLAGGED, never failed: whether the ZOMBIES tests really cover the letter, an N/A reason that is not credible, the layer consumed and the dependency order, a unit test file with no test double, a trivial stub, whether the unit tests drive real design, production-side weakening in the green commit.
- Implications for card mode: the red seat writes ONE acceptance test for ONE criterion, not the whole card; the inner loop is unit red, green, refactor from the outside in with doubles; the acceptance criteria and the unit tests of every layer are derived with ZOMBIES; the acceptance test stays red until the last unit lands; then the next criterion starts; the records show the sequence per criterion and the ZOMBIES tests per layer (or N/A because per letter). A card with one criterion and many layers stays thin because the slice is three reviewable increments within the criterion (acceptance red; ordered layer-completion unit commits; acceptance green).
- Open: the checker, the pending-red job and the trail record fields are not implemented yet (a card after card 195); card mode prompts for the red and green seats must change to this sequence.
- Reversal: documents and later checks; removing the pending-red job turns the proof of real red off, which the external audit notices.
