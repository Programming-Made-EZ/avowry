Facts: the v0.1 bar names Dana, a .NET developer who directs an AI agent, as the sole preview persona ("the smallest thing that is honestly useful"); bar 1 says install is on stated systems with the supported .NET SDK; D121 accepted this (2 Support-it to 1 No; its three seats shared one persona and none raised audience breadth). Card 176 closed as a dotnet tool (PackAsTool, command avowry, version 0.1.0). From `avowry build` to a running API a user needs the .NET 8 SDK: the adapter emits csproj files with net8.0 (src/Avowry.Adapters.CSharp/CSharpProvider.cs lines 157 and 170) and the demo README runs dotnet build, test and run on the output; no global.json. So the build, the specs and the run need the SDK however the CLI is distributed; only the compile step could run without it. Not stated in the repo: whether the framework-dependent CLI needs the SDK or only the runtime (a tool property, unconfirmed); whether `avowry trace` needs the SDK.

Audience: Dana is the right sole persona for v0.1 (a Dana without .NET has nothing to build); Ari (the primary customer) runs in Dana's environment and uses the same CLI, so Ari is served by docs and diagnostics (cards 179, 182), not by packaging; Morgan (reviewer) can read `.avowry` and the specs without .NET (passive use, nothing to run); an AI-directing developer without .NET could install a binary and read generated C# but could not verify, run or ship anything, so the bar's verifiability pay-off would be unavailable. No evidence in the repo of a wish for a non-.NET preview audience (VISION.md puts multi-language in adapters, C# first, and synthesis from existing code in any language in a later milestone; nothing in feedback, benchmarks or rulings asks for a broader preview audience).

Distribution options: self-contained per-platform binaries remove the need for a runtime for the CLI only, not the SDK for the output (medium: a build matrix, signing and notarisation; risk: it implies "no .NET needed", which is false); winget, Homebrew and npm wrappers are discoverability only (medium each, plus maintenance of feeds; risk: a package name and ownership is a one-way door on each feed, bar 7); a container image is the only option that bundles the SDK, so it gives a non-.NET developer an end-to-end path with no local install (medium to large: image publishing, mounts, running the API from a container; risk: new surface for every bar before any user has asked). It changes what is possible, not the recommendation.
