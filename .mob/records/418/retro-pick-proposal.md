THE PROPOSED ENTRY (verbatim from the patch):

- **A gate records the toolchain version before and after and refuses a verdict when it changed (experiment; card 418 retro, Decider D251).** While this entry is on trial: every facilitator baseline gate and every sign-off run prints `dotnet --version` (and the versions of the other toolchains the run uses, such as `python --version`) before the run and again after it, into the gate summary or the sign-off reply; the comparison is made by a committed script, never by reading: `scripts/gate_stamp.py before FILE` and `scripts/gate_stamp.py after FILE` write the stamp (the versions, and the sorted names of the SDK folders of the dotnet installation as supporting evidence) and, on `after`, compare it with the `before` stamp and write the line `VOID: toolchain changed` into the file and exit with status 3 when a version or the set of SDK folders differs, so that a void verdict needs no human review; a void run is not recorded as a pass or a failure of the card, its logs are kept with a note, and the run is repeated on the new toolchain; the facilitator's gate scripts and the sign-off prompt call the script; until the script exists (a tooling card, written red first and filed with this pick) the facilitator prints the two version lines by hand; the independent gate reviewer checks the stamp in the gate records.
  - Hypothesis: an environment update during a run is not scored as a card failure, and no contaminated verdict is accepted. Metric: gate verdicts accepted although the toolchain changed during the run (card 418: 1, a .NET SDK update installed mid-gate gave 13 simultaneous failures, found by reading timestamps and one error), target 0. Counter-metric: seconds added per gate (target under 5) and benign version-string changes that void a run. Trial: the next 3 cards with a baseline gate, counted from Decider D251. Owner: the facilitator. Review at the third card's retro: keep, change or remove.
