# Avowry as a stand-alone language: the PM and architect revisit (the product owner's framing, 2026-11-07; Dispatch's direction for the team to weigh, not a ruling)

Two read-only seats, fresh contexts (product manager and architect); facts from the repository and the driver survey; nothing was built or run. Inputs: the framing (Avowry is its own language with LLMs as the JIT runtime; .NET is an adapter target; stand-alone; core toolchain as one native binary; adapters as add-on plugins; core library as Avowry source; `avowry mcp` and a language server in the same binary; later a Wasm build of the toolchain), the owner's preference for WebAssembly (input, not a ruling), the owner's three answers (start the survey now; the second-target story ranks after the v0.1 bars, revisitable; new personas only if the survey shows demand), and the survey (.mob/records/platform-options/driver-survey-2026-11-08.json: Grok, Muse, Cursor and Claude all put Python and TypeScript/Node first, about 65 to 75 percent of the HTTP services they are asked to write, Go 10 to 15 percent, C# about 10 percent or less; containers on cloud then serverless; agents mostly run code in Linux sandboxes or not at all; all four say a language compiling to their common stack beats .NET-only; self-reported impressions, not telemetry; Codex, Copilot, agy and local Qwen not asked).

## Recommendation (both seats agree)
Keep the v0.1 preview on its schedule with no new gating cards, and change what it claims: "the C# adapter preview, installed through one channel (the dotnet tool)", not "Avowry runs on .NET". Do it by amending three open cards at their Ready steps, not by adding cards: card 179 (the README and guide: the first screen says Avowry is its own language and C# is the first adapter), card 178 (prerequisites: requirements per component; the page just written says what the C# route needs), card 186 (the known-limitations page, issue 186 titled 187: the core compile also needs .NET today). Reasons: the repo shows v0.1 bars 1, 2, 3, 4, 6 and 8 as C#-shaped (bar 1 the dotnet tool and an SDK, bar 2 a guide that runs dotnet build, test and run, bar 3 the Tasks demo with 5 native C# blocks, bar 4 a source map and trace carrying C# file and method names, bar 6 a C# fixture corpus, bar 8 "C# and FastEndpoints only"; bars 5 and 7 are neutral apart from the name check, which covers NuGet only and must also cover any new channel); holding the preview for stand-alone would delay it by an unsized amount; the first public claims are a one-way door, so card 179's wording needs the amendment before it is pulled.

## Two facts the framing hides (PM and architect)
1. The CLI has no spec runner: specs are generated xUnit tests run by `dotnet test`. "No .NET needed" would be true for compiling and checking but false for verifying until specs can run without a target toolchain. The core can check and trace; it cannot run specs until a target runs them.
2. What makes Avowry not stand-alone today (architect): the CLI is a dotnet tool (`PackAsTool`); the C# provider is compiled into the CLI (`new CSharpProvider()`, `--target` accepts only `csharp`); `trace --assembly` reads .NET metadata (the build-id check, PEReader and MetadataReader); specs are emitted as xUnit; `native csharp` blocks only mean something to the C# adapter (a leaf with no block for the selected target fails with PH020).

## Feasibility per framing point (architect)
1. Native AOT of the compiler and CLI: size S to M, risk low to medium. The CLI references only the compiler and the C# adapter (no packages, no Roslyn, no `Process`); no reflection beyond a few Regex, typeof and GetType uses. Three things could block it: `JsonSerializer` on the map records through reflection (analyzer warnings IL2026 and IL3050; `TreatWarningsAsErrors` is on; a System.Text.Json source-generated context, about 10 lines); the build-id reader (plain library code, should work); `--version` reading `AssemblyInformationalVersionAttribute` (probably works). The cheap check: `dotnet publish src/Avowry.Cli -c Release -r win-x64 -p:PublishAot=true`, then `linux-x64`, then diff `avowry build` output against the JIT build (the repo's tests already pin generated bytes), and record the binary size.
2. Add-on adapters: size M to L. Loading adapter DLLs at run time is hostile to AOT and trimming (not pursued). The better route: out-of-process adapters speaking JSON over stdio (the core sends the module model; the adapter returns the path-to-text file map, which is already the shape of `CompilationOutput.Files`), so a TypeScript or Python adapter can be written in its own language. Prerequisites: generalise `EndpointFiles`, `AvowFiles` and the map records (`csFile`, `csMethod`, `csHash` are C#-shaped) and document a JSON schema for the module model: that schema is the real cost.
3. Core library as Avowry source: size L, design unknown. Today the core is the keywords in ExtensionKeywords.cs (only `uses web`), `ensure` is a built-in construct mapped by the adapter to a guard clause (D105 layer 1, card 159), the D95 store convention lives in the C# adapter and is provisional; the repo has no Avowry-source library, no import or module mechanism and no registry or git-URL loading.
4. `avowry mcp` and a language server: size M each; neither exists; compilation stops at the first failing phase, so editor feedback would be coarse; a JSON-RPC layer is the only new dependency (hand-rolled to stay AOT-friendly).
5. Wasm: two separate projects. Compiling the compiler to Wasm looks plausible (the core is pure string-in, string-out) but needs a .NET WASI toolchain whose maturity the repo cannot judge; spike: compile Avowry.Compiler to a WASI module that reads source on stdin and writes the file map as JSON. Emitting Wasm programs is a new adapter (M to L): failure, effect and store conventions in WASI terms; HTTP and persistence depend on host support (WASI HTTP and sockets, the component model); the source map changes from C# method names to a Wasm mapping and the build-id check cannot read .NET metadata. The owner's suggested spike (a leaf, a failure, a spec compiled to a Wasm component, run under Wasmtime, a failure traced to its spec line) is the target spike (M to L).

## Proposed stories (PM; each a product story with a consumer; ranked after the v0.1 required cards 179, 186, 162, 189 and 188 (publish), above 325, and after 201)
- S1 A single native binary: As Dana, I want to install Avowry as one native binary with a one-line script, so that I can compile Avowry source on a machine without .NET. [O] Given a clean Linux container with no .NET, when I install and run `avowry build Tasks.avowry`, then it exits 0 and prints the C# project path. Size M; depends on 176 (done); first of the six, right after 188. Unknown: whether the compiler and CLI compile ahead of time (the AOT publish check above); under the spike rule a spike is allowed only once S1 is the top story. The winget, Homebrew and Scoop names are new one-way doors (bar 7).
- S3 A tiny program in Python or TypeScript (the survey's demand): As Dana, I want one tiny program to produce passing specs in Python or TypeScript, so that I can keep my stack. [O] Given the same leaf, failure and spec, when built for the target, then the specs pass. Size M; depends on S1 only for packaging; absorbs card 108 (specs only, Ready) and narrows card 028. On the evidence ranked above S2; the final order is the owner's call.
- S2 Wasm feasibility (the owner's step): As Ari, I want one tiny program (a leaf, a failure, a spec) compiled to a Wasm component and its specs run under a WASI host, with a failure traced to its spec line, so that I can verify code inside a sandbox with no language runtime. [Z] Given the program, when its specs run on Wasmtime, then they pass and a forced failure names the spec line. Size L; depends on S1; unknowns: what emits the Wasm, whether the host is bundled or a separate tool, the Wasm source-map shape; it forces the source map and trace to become target-neutral.
- S4 `avowry target add`: As Dana, I want `avowry target add csharp`, so that the .NET SDK is a requirement of the C# adapter alone. [I] Given the core without the adapter, when I build for csharp, then it names the missing add-on and the command. Size L; depends on S1 and on S2 or S3, so the plugin shape comes from two real adapters; risk: an AOT binary cannot load plugin assemblies, so adapters are probably separate processes or Wasm modules (unverified).
- S5 Core library as Avowry source: As Ari, I want the standard patterns (ensure, record update) shipped as readable Avowry source versioned with the toolchain, so that I read what a pattern means instead of inferring it. [S] Given `ensure`, when I open the library, then its spec shows the failing and passing case. Size M; depends on S1; unknown: how much of D105's layer 1 is compiler built-in versus expressible as source; registry or git-URL modules: no consumer has asked, so no story.
- S6 `avowry mcp`: As Ari, I want check, build, spec and trace as MCP tools in the same binary, so that I get structured diagnostics with location and fix. [E] Given a source error, when called as a tool, then the reply carries code, line and next action. Size M; depends on S1; ranks last; the demand evidence is weak (the survey does not mention MCP). A language server and the Wasm toolchain build stay parked until S2 has run.
- Card 336 (a container image with the CLI and the SDK): keep it unranked; the framing makes it a stopgap.

## Recommended sequence (architect)
1. The AOT publish check (an Unknown; a spike only when S1 is the top story). 2. Make the map and trace independent of .NET (a story with a consumer; the existing trace tests pass). 3. Define the adapter JSON protocol and move the C# adapter behind it; a tiny second adapter in TypeScript or Python is the evidence that the module model is language-neutral (and it exercises the survey's top audience). 4. `avowry mcp` after step 3, with a consumer story first. 5. The compiler-to-Wasm spike after step 1. 6. A Wasm target or an Avowry-source core library: park until a consumer asks; the library needs a design decision first.

## What the seats could not verify
Whether AOT publish succeeds or the binary size; whether Regex, typeof and GetType in the compiler and C# adapter are AOT-safe; whether a .NET-to-Wasm/WASI path exists and is mature; WASI HTTP and component-model support in Wasmtime or Wasmer; any repo design for a registry or git-URL modules, a UI grammar or the Wasm browser-container idea (the repo has none); the effort figures are estimates from the structure of the code; the survey is a self-report of four drivers.
