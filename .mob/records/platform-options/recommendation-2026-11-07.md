# Platform options for Avowry: consumers first, then target/runtime and toolchain/distribution (the product owner's direction, 2026-11-07; a proposal to explore, not a ruling)

Two read-only seats, fresh contexts: the product manager seat (consumer research) and the architect seat (options comparison). Facts from the repository; nothing was run. Their replies are summarised below; the facilitator's synthesis and recommendation are at the end.

## Consumers (product manager seat)
- Today, from the repo: Ari (cold-start agent; the primary customer; runs in Dana's environment; deploys: not recorded), Dana (a .NET developer who directs an agent; .NET 8 SDK; the emitter writes net8.0 projects with FastEndpoints on ASP.NET Core; where Dana deploys is not recorded), Morgan (reviewer; can read `.avowry` and the specs without .NET, passive use), Riley (the mob dogfooding; not a platform consumer), Steve (board and tooling).

Dana and Morgan need C#/.NET 8 now; H1 needs a second target in their language and an install without .NET; H2 needs little toolchain (CI builds); H3 needs a profile file; H4 possibly Wasm or in-process and a library.

## Options comparison (architect seat)
- What the adapter contract already separates: the compiler (lexer, parser, resolver, `ModuleModel`) and `ITargetAdapter { Target; Emit(ModuleModel) }` returning a path-to-text map plus `EndpointFiles` and `AvowFiles`; D54 pinned this with a substitute-adapter test; the grammar already lists native targets `csharp | typescript | python` (GRAMMAR.md line 5: "C# first, then TypeScript, Python"). A second adapter must supply, following CSharpProvider.cs (983 lines): a project or manifest and a specs project, a runtime shim (a failure type with a code and an `[Avow]` attribute), host bootstrap and dependency injection, type mapping, one function per avow (native body or lowered steps) with the effect-to-parameter convention, one endpoint file per endpoint with the failure to HTTP 422 mapping, executable specs for every outcome kind, effect doubles and the provisional `{Record}Store` convention (D95). Cost drivers: specs and doubles generation, the effect and store convention, async versus sync, endpoint binding to a web framework, type mapping; the step lowering is small; the web boundary is already partitioned (ExtensionKeywords.cs, D93), so core-only programs could go first.
- Not as neutral as it looks: the source map and `trace` live in the CLI, not in the compiler or adapter; records carry csFile and csMethod and a C# file hash; the build-id check reads .NET assembly metadata; the `EndpointFiles` and `AvowFiles` shapes are C#-shaped; the CLI accepts only `--target csharp`. A second target needs this generalised, a cost of its own. Native blocks are keyed per target (a leaf needs a block for the selected target or PH020); the Tasks demo has 5 native C# blocks bound to the provisional store interface; composites and endpoints are pure composition and transpile with no per-target code.
- Target/runtime options (reach; fit with verifiability, preserved intent and reviewability; cost to emit; main risk):
  - Managed C#/.NET (today): the .NET developers; specs run as xUnit and trace works; done; narrow audience; the SDK is needed to build and run the output however the CLI is shipped.
  - Python or scripting: the largest AI-directing audience (an inference, not repo evidence); specs run as pytest, dynamic typing weakens the checks on holes; medium; every native block rewritten and the failure and effect conventions invented again.
  - TypeScript/Node (named in the grammar): web developers; same shape as Python with static types; medium.
  - C++/Rust/native: systems; specs run but heavy; large; the cost far exceeds any audience evidence.
  - WebAssembly: browser and edge; specs could run in a Wasm host, trace needs a new map; medium to large, it is a compile target plus a host; ecosystem gaps for HTTP and persistence.
  - JVM: enterprise; JUnit; medium; no demand shown in the repo.
  - A custom Avowry runtime: highest fit in principle (undeclared effects and failures refused at run time, specs and trace native); large (web, persistence and test tooling rebuilt); the specs would run under the same system that runs the code, which weakens independent verification; distribution of a new runtime is a new one-way door; D74 favours deterministic compilers per target.
  - Browser Wasm containers (parked): no design exists in the repo; needs the compiler in Wasm, a target that runs in Wasm and an extension-loading model; risks: supply-chain trust of extensions at git URLs and no persistence or HTTP in a tab.
- Toolchain and distribution: the dotnet tool (done, card 176; fits the C# output that needs the SDK anyway); a self-contained AOT CLI (removes the runtime for the CLI only; "no .NET needed" would be false for the C# target; pays off only with a non-.NET target); the compiler as Wasm (plausible, unverified; a browser playground or Wasm container); a rewrite in another language (large; no evidence); hosted compile (small to medium; sends source off the machine; the repo is silent); a container image with the CLI and the SDK (the only option that bundles the SDK for the C# target; story 336). The two questions are independent except for the AOT row.
- Not verified: second-adapter cost estimates (inferred from the C# provider's structure), whether the compiler compiles to Wasm or AOT, any consumer demand beyond C#, whether the installed tool needs the SDK or only the runtime.

## Recommendation (facilitator's synthesis; for the product owner)
1. Keep the v0.1 preview .NET-first (unchanged; the PM seat's earlier answer stands; cards 177 to 188 proceed). The reasons now have two sources: no recorded consumer demand outside .NET, and a second target is not a packaging change: the contract is language-neutral in the compiler, but the source map, trace, build-id check and the endpoint and avow file shapes are C#-shaped, and every native block and the store convention would be rewritten.
2. Question 1 (target and runtime): gather evidence first, cheaply and in this order. (a) The driver survey: one question to each available driver ("what language and framework are you most often asked to write HTTP services in, and what would you deploy them on?"), which is the LLMs-are-the-customers rule and takes minutes; Codex, Copilot and agy answer when their quota returns. (b) A second-provider story for one tiny program (a leaf, a failure, a spec, no HTTP) in TypeScript or Python, using the existing cards 028 (a TypeScript spike) and 108 (TypeScript or Python, specs only) as the home, to learn what is truly language-neutral and whether the source map generalises; note the spike rule: a spike is allowed only to unblock the story at the top of the board, so this goes as a product story with a consumer (H1) and a Gherkin scenario, ranked at a re-rank, not as a standalone spike. (c) A source-map generalisation probe (can csFile, csMethod and the assembly check become target-neutral without breaking the C# map, schema version 1): a story with Morgan or Dana as the consumer. (d) A Wasm feasibility probe (compiler under .NET Wasm; a C#-emitted program as Wasm; time and size): park until a consumer asks.
3. The custom runtime and the browser Wasm containers: park until a consumer asks, per the value rule. The architect's caution: a custom runtime would hold effects, failures, specs and trace natively (the strongest fit with the AI-accountability purpose) but it would put the specs under the system that runs the code and it rebuilds web, persistence and test tooling; the cheapest way to learn whether it is worth it is the second-provider story, not a runtime.
4. Question 2 (toolchain and distribution): keep the dotnet tool; the container-image story 336 stays unranked until a reopen condition holds (a second adapter exists, a reader asks for a non-.NET route, or the cold-model run shows SDK setup friction); self-contained binaries and wrappers wait for a non-.NET target.
5. Decisions that are the product owner's: whether a persona for an AI-directing developer on a non-.NET stack (H1) and an operator (H2) should be added to PERSONAS.md now (the persona rules need the owner's ruling on audience before a persona is added); whether to start the driver survey now; whether the second-provider story should rank above or below the v0.1 bars (the seats recommend after the v0.1 bars, and not before the survey's evidence).
