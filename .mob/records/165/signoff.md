## Named limits

1. **R165-3 follow-up F5 (duplicate declaration-line selection rule)**: `SourceMapIds.StepId` is unified in `Avowry.Compiler`, but the logic for determining which declaration line to feed into the step ID is duplicated between CLI (`Program.cs:336-345`) and adapter (`CSharpProvider.cs:364-386`). While textually equivalent today, moving this into `Avowry.Compiler` next to `SourceMapIds.StepId` (e.g. `SourceMapIds.FailureDeclaration(module, endpoint, failure)`) is a named follow-up.
2. **R165-3 follow-up F7 & review-grok.md MINOR 1 (unbounded Task.Run thread-pool sharing)**: In `CSharpProvider.cs`, each 422 response queues a work item via `Task.Run`. If a consumer registers a slow or blocking synchronous observer, a flood of 422 requests could starve the thread pool workers, acting as a DoS amplifier. Bounded dispatch / queued worker for failure events is a named follow-up. Documented in `docs/TRACEABILITY.md` that `OnFailure` must be fast, non-blocking, and synchronous.
3. **R165-3 follow-up (effect named AvowryFailureObserver)**: If a Phrase module defines an effect named `AvowryFailureObserver`, the generated effect types could collide with the generated observer types/file in the module namespace.
4. **review-2.md R2-1 (empty switch block warning CS1522 on undeclared-only failures)**: If an endpoint's only failures originate from endpoint-level constructs without a `fails with` declaration (e.g. `ensure ... else Code` or `fail with Code`), `FindFailureDeclaration` returns null, emitting `switch (failure.Code) { }` and triggering compiler warning CS1522. Recommended follow-up: replace `endpoint.Failures.Count > 0` with a predicate checking whether the endpoint has at least one failure with a declaration at all four emission sites (constructor parameter, catch call, helper emission, and spec `Factory.Create`).
5. **review-2.md R2-2 (theory equates declared with endpoint.Failures)**: `The_catch_builds_one_event_per_declared_code...` takes `declared = endpoint.Failures`. This holds for Tasks and orders where every failure is declared, but would diverge on a module with endpoint-level undeclared failures.
6. **review-2.md R2-3 (TRACEABILITY doc wording precision)**: `docs/TRACEABILITY.md` states "Only declared failure codes are observed", which is slightly loose because endpoint-level `ensure ... else Code` is a failure but unobserved. Clarification nit: "Only failures that a `fails with` declaration reaches are observed (the same failures that have a map record)."
7. **review-grok.md MINOR 2 (`async void OnFailure` process teardown)**: The dispatch wrapper `try { failureObserver.OnFailure(observed); } catch { }` catches synchronous exceptions. If an observer implements `async void OnFailure`, an unhandled exception thrown after an `await` escapes outside the catch onto the thread pool and may fault the host process. Documented in `docs/TRACEABILITY.md` that implementations must not be `async void`.
8. **review-grok.md MINOR 3 (`FailureStepIds` reserved name)**: In the initial green, `FailureStepIds` was generated in the module namespace without being listed in `ReservedNames.TypeNames`. Resolved in R165-3 / green round 2; reserved name diagnostic AV341 now guards `FailureStepIds`.
