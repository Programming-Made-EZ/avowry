## One id scheme (card 161's)
The step id is computed today only in the CLI (`StepId`, src/Avowry.Cli/Program.cs about line 130: sha256 of `kind\nline\nname` plus `\nendpoint` for a failure, normalised). Move that rule into `Avowry.Compiler` (one public static method, for example `SourceMapIds.StepId(kind, line, name, endpoint)`), and make both the CLI map writer and the C# adapter call it. The map bytes must not change (card 169's MapCultureInvariance and the existing map tests).

## Generated runtime (C# adapter, src/Avowry.Adapters.CSharp/CSharpProvider.cs)
- A new generated file in the API project with a reserved name (add it to ReservedNames): `public interface IAvowryFailureObserver { void OnFailure(AvowryFailureEvent failure); }`, `public sealed record AvowryFailureEvent(int SchemaVersion, string Code, string Endpoint, string StepId, string BuildId);` (SchemaVersion 1) and `public sealed class NoOpAvowryFailureObserver : IAvowryFailureObserver` that does nothing.
- The generated host (Program.cs emission, about line 307) registers the no-op with `TryAddSingleton`, so a host can register its own observer first or replace it.
- Each endpoint that can fail receives the observer (constructor injection) and, in its `catch (AvowryFailure failure)` block, after the 422 is decided, builds the event from compile-time constants only: the code, the endpoint name, the step id for that code and endpoint (computed by the shared rule at generation time and emitted as a constant lookup), and the build id (the same value as the AvowryBuildId assembly metadata). No request data, exception message, file name, line or spec text is in the event or in the generated lookup.
- The observer call cannot change the response: it runs after the 422 response is sent, wrapped so an exception is swallowed, and off the request path so a slow observer does not delay or alter the response (for example a fire-and-forget task with the exception observed). The red's tests decide the exact form by behaviour: a throwing observer and a 5-second observer each leave the 422 status and body unchanged, and the slow one does not delay the response by more than a small bound.

## Trace and the logging line
- `avowry trace` accepts a step id as its query (an exact match on a record's stepId), besides the existing names and frames.
- A plain logging observer (in the test project, and shown in docs/TRACEABILITY.md) writes one production-shaped line, for example `avowry-failure v1 code=EmptyTitle endpoint=CreateTask stepId=<id> buildId=<id>`; feeding its stepId to `avowry trace --map` resolves the failure to its exact avow file line and endpoint.
