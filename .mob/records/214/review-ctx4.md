## Findings

1. LOW, Support/GeneratedApi.cs:145-196 (WaitUntilListeningAsync): the 500 ms ExitSettle is a heuristic, not a guarantee. Needed for guard 6 (a child that prints its address and leaves still accepts a connection briefly) and correct for that case: HasExited is checked before each probe and again after the settle, and the exit message drains both pumps. Cost: a fixed 0.5 s per successful start (about 15 real-API starts plus QuietChild starts in the suite, run in parallel, so well under 10 s of wall time). A real Kestrel prints the line only after it is bound and the hosted services started, so "prints then dies within 500 ms" is rare; a death after 500 ms is caught by the test's first request. Not in the slice: it is disclosed in the commit 5 body. Fix: none required; add one comment line saying 500 ms is a bound on the print-then-exit race, not a proof.
2. MEDIUM (process, not code), commit 5b afa4e40 Support/ThreadPoolFloor.cs:12-16: a global SetMinThreads(128,128) module initializer. It is a mitigation of the starvation, not a removal of its source: the sources are the sync ReadToEnd/WaitForExit calls on pool threads in other test classes. It is test-assembly only (net8 has no AppDomain split; process-wide for the testhost only) and changes no assertion. The diagnosis in the commit body (line already in the log, waiter continuation late) is plausible and consistent with my numbers (see F-062). Side effect: other tests see a different thread-injection schedule; none failed because of it in my runs. Fix: call it a mitigation in the comment, and file the sync-over-async tests as a bug card; do not claim "cause-level".
3. LOW, Guard_hook_is_null_by_default_and_fires_once (GeneratedApiSeams.cs:20-45): the admitted blind spot (hook called twice) is real for this test, because its hook throws on the first call. It is covered elsewhere: Guard_bind_failure_starts_exactly_one_process counts starts through a non-throwing hook and asserts 1 (GeneratedApiBoundAddressEdges.cs:152-163). So a double Invoke turns that guard red. Accepted; fix optional: name that cross-cover in the guard 1 comment.
4. LOW, kill discipline: DisposeAsync (GeneratedApi.cs:104-129) kills only `_process` when `_process.Id == Pid` (recorded at construction); the child is `dotnet <dll>` with no wrapper, one PID. Unchanged by the card. RunToEndAsync likewise kills its own PID. Verified by reading both and by the source scan checked set. No finding.
5. INFO, ubuntu CI: no flakiness source found in the card's code. Path is case-correct (QuietChild.dll), net8.0, `Now listening on:` is parsed per line and unanchored, the env override `Logging__LogLevel__Microsoft.Hosting.Lifetime` is valid on Linux, HTTP(S)_PORTS and DOTNET_URLS are cleared. Residual risk: fewer cores on ubuntu-latest (4) make pool starvation worse than here (16), which the floor helps. The first ubuntu CI run on afa4e40 is the evidence the slice names.

6. MEDIUM, GeneratedApiBoundAddress.cs:~20-27 (Z_a_child_that_never_reports_an_address_times_out_naming_pid_url_0_and_log): StartupTimeout is 1 s and the test asserts the message contains the child's log line "z-log-line". Under load the QuietChild (a cold `dotnet` start) had not printed within 1 s, so the timeout fired with an empty log: in my floor run (3 suites at once, so about 3x the load of one run) it failed in 1 s with "Not found: z-log-line". This is a real flake, independent of the thread-pool floor, and will bite a 4-core ubuntu runner. Fix: raise the Z StartupTimeout to 5 s (still fast), or print the line first with --print and wait on a gate the test releases only after the line is in api.Log is not possible before StartAsync returns, so the 5 s window is the simple fix. Same check for the other short windows (3 s B host cases passed in the floor run; they took 3 s and 16 s in the author's pre-floor run, so keep an eye on them).

Reading:
- The slow path exists on the old harness. The old harness needs 10 s median and up to 63 s to become ready under full-suite load, and it failed UsableV1.Bar5_the_app_runs_and_live_http_matches_the_specs after 4 m 56 s ("request canceled due to the configured HttpClient.Timeout of 30 seconds"): the very test that failed in CI run 41020033271 for F-056. Its 2-minute window was absorbing a startup that already took tens of seconds. Typical single-start time is the same across trees (median 10.1 s vs 9.1 s vs 7.5 s): the new harness does not make a start slower.
- The new harness adds no blocking thread demand: per start it uses two ReadLineAsync pump loops (as the old one did), one TaskCompletionSource and WaitForExitAsync, plus a 200 ms Task.Delay probe loop (the old one also polled with Task.Delay(200)). Nothing blocks a pool thread. What it adds is shorter windows in its own tests (1 to 20 s) and about 25 more child processes from the card's tests (QuietChild starts, two extra real APIs), which add load to the shared pool and CPU.
- Without the floor the new tests and several real-API tests starve: NOFLOOR failed 21 (9 card tests, among them O and Hazard_a after 3 m 03 s and 3 m 45 s, and 5 older real-API tests, EndpointFailure, TasksOverHttp Twenty_parallel, PutAndDelete, SourceMap, Bar5, at 2 m 38 s to 3 m 27 s), OLD failed only Bar5 of those. p90 ready time 68 s vs 16 s. This is the direction the author reported, but one sample at 3x load cannot separate "the new harness is more sensitive" from "the card's extra tests add load". UNPROVEN as to which of those two it is.
- With the floor the picture is the old one or better: FLOOR failed 10, none of them an older real-API test; 8 are the environmental set (PrivateHoldoutResults x2 and HoldoutTaskConversion need a git checkout, which my scratch copies lack; Bar6 stale evidence; CSharpBaselineAcceptance x4 with `dotnet_test_timeout` from nested `dotnet test` in tools/Phrase.Bench under load) and 2 are load flakes (BenchmarkHarnessAcceptance.timed_out_model_tree... The CSharpBaselineAcceptance failures occur in OLD too (wrong_reply 2 m 47 s, zero_executed 3 m 20 s, both endpoint_reply), so they are not caused by card 214.
